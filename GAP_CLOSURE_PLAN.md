## D. Feature Timing Decision and Baseline Comparison

### Recommended default

Use transactions with `transaction_date < loan_date` as the corrected cutoff unless authoritative source data establish an unambiguous within-day order. This excludes all transactions from the issuance date and later while retaining earlier history. Do not simply filter out the 122 affected loans: that would change the population and could create selection bias. Do not infer transaction order from row order or transaction IDs without documented semantics.

Before implementing, inspect the raw date representation and source documentation to determine whether any time-of-day field exists outside the current processed columns. Confirm date parsing and whether loan date means the exact prediction/origination date. If no finer timestamp/order evidence exists, record that the strict prior-day cutoff is a conservative operationalization, not proof of intraday timing.

### Comparison design

1. Freeze current analytical data, model artifacts, saved predictions, metrics and explanations as the **inclusive-cutoff baseline**; do not overwrite them.
2. Generate a versioned corrected analytical dataset with the same loan population and target mapping, but features based only on dates strictly before loan date. Record for each loan the count of same-day and later transactions excluded and the pre-cutoff history availability.
3. Compare baseline and corrected feature availability/counts, then run the approved train/validation/test workflow separately on each dataset with the same test membership and split protocol wherever feasible.
4. Report both results in separate columns/tables, explicitly attributing any difference to the corrected feature cutoff plus any other approved change. If several changes are combined, avoid attributing metric changes to one cause; use staged versioned comparisons where practical.
5. If a loan lacks usable prior-day history, apply only an approved, documented policy (e.g. a training-fitted imputation plus missing-history indicator if supported, or a separately counted exclusion sensitivity analysis). Do not silently drop it or fabricate history.

**Approval needed:** strict previous-day cutoff versus any source-supported alternative, and what to do with loans that then have no usable prior history.

## F. Model Selection, Validation, and Test Protocol

### Proposed workflow

1. **Lock data and split membership.** Keep the current primary test loan IDs and rows exactly as stored. Record the two shared calendar-date boundaries. Because dates have day precision, describe the split as row-ordered by date, not as an exact within-day temporal ordering. Do not rebalance or reshuffle test.
2. **Feasibility check for inner folds.** Count defaults by date and by candidate expanding-window fold in the training partition. Select a small number of forward-chaining folds only if each relevant validation fold has both classes and enough cases to compute the planned metrics. Save fold definitions. Do not set an arbitrary number of folds before seeing these counts.
3. **Tune only on training.** Use forward-chaining/expanding-window folds inside the training period. Optimize the predeclared primary tuning metric; retain ROC-AUC as the current grid-search baseline and report average precision as an imbalance-sensitive companion. Save fold-level metrics and date ranges. Any search-space change is documented.
4. **Fit preprocessing within each fold.** Use a scikit-learn `Pipeline` (or equivalent) so StandardScaler for LR and any future learned transform is fit only on each fold's training indices. Constant missing-value handling does not learn data statistics, but missingness should still be monitored. For XGBoost class weighting, ideally derive `scale_pos_weight` from each fold's training labels; if that cannot be supported cleanly, disclose that the fixed training-wide ratio uses labels from inner validation folds and seek approval for the alternative.
5. **Refit each selected candidate on all training rows.** The validation and test partitions are excluded from this fit. Persist the exact parameters and model/feature schema.
6. **Validation selection.** Compare the three fitted models using a predeclared set of approved metrics on validation. No single “best” metric should be invented after seeing results. Given the imbalance, report PR-AUC/AP and precision-recall alongside ROC-AUC, Brier, and threshold metrics. Select the model using an approved rule before reading test outcomes.
7. **Validation threshold policy.** Report 0.5 as baseline. If a non-default threshold is required, predeclare a validation-only criterion. With no institution-specific costs, threshold results are methodological tradeoffs, not a lending policy. Record the chosen value, the full validation precision/recall/F1 tradeoff, and freeze it before test access. Do not optimize or revise it using test labels.
8. **Final evaluation.** Evaluate the frozen model(s) and threshold(s) once on the unchanged primary test rows. Report existing unmodified baseline and corrected-version results separately. Recalculate all approved metrics and standard `[[TN, FP], [FN, TP]]` matrices. Interpret estimates in light of only three positive cases.

### Methodology status and departure

The approved commitments require a chronological primary split and an approved cross-validation procedure, but the specific CV design is not documented in the audit. Switching from shuffled stratification to forward-chaining CV is a **proposed methodological refinement** to align inner validation with the temporal prediction setting; it is not silently assumed to have prior approval. It changes the tuning evidence and may change selected parameters, but does not change the primary test cohort or the model families. Obtain approval before implementing.

Using the previously unused validation set for model/threshold selection completes the approved train/validation/test roles; it is not a test-set change. However, validation has only 18 positives and is reused for decisions, so selection uncertainty and potential validation overfit must be disclosed.

**Approval needed:** inner-fold design/count, primary tuning/selection criterion, whether threshold selection is required beyond 0.5, and whether final model remains fit on train only (recommended for clarity) or any later refit is permitted.

## G. Explainability and Stability Minimum

### Minimum additional explainability set

- **Global SHAP:** for the selected final model, publish mean absolute importance and a summary/beeswarm plot with feature units/definitions. Add dependence plots for a small set chosen before inspecting test outcomes (suggestion: top features from training-only analysis, or a predeclared domain set). Explain direction and interactions as model attribution patterns, not effects or causes.
- **Local SHAP:** produce at least three validation examples chosen by a deterministic, predeclared rule that does not use target labels (for example, low, middle and high predicted-risk ranks, with a tie rule). A case description should be anonymized and limited to feature values needed to interpret the attribution.
- **Candidate LIME:** run on the same validation cases and selected model so the methods can be compared case-by-case. Record random seed, discretization/kernel settings, perturbation/background source, number of features and local fidelity. Test compatibility first; if fidelity or stability is poor, report the failure/limitation rather than forcing a persuasive explanation.
- **Test separation:** do not use the test set to choose features for dependence plots, case identities, explanation method/settings, a preferred model, or threshold. If test explanations are retained for final descriptive reporting, predefine the exact procedure and generate them only after model/method choices are frozen. They must not feed back into selection.

### Defensible stability procedure

Use feasible expanding-time folds contained in training. Freeze hyperparameters after the training-only search. Refit one model per fold using only that fold's earlier training rows and fold-local preprocessing. Explain the same fixed non-test reference feature matrix for every fold model, preferably a designated validation cohort after selection rules are frozen, so ranking differences are less confounded by evaluating different cases. Use the same SHAP output scale and feature set. Compute all pairwise Spearman correlations of mean absolute SHAP rankings, report each pair/fold dates, valid pair count, mean, SD definition, and limitations. If the selected reference cohort is also used for model selection, explicitly state this and ensure stability outputs do not drive another model change.

For technique comparison, compare SHAP and LIME on matched cases and report agreement/disagreement descriptively; do not treat correlation as proof that either explanation is correct. Similar-case explanation variability is optional unless the approved final implementation specifically requires it; feasibility and definition of “similar” must be approved first.

**Feasibility gate:** verify XGBoost/SHAP API behavior on one fold and one case, and LIME package compatibility/fidelity on one validation case before committing to full analysis. These are implementation probes only after authorization; no such probes are performed by this planning task.

## H. Computational Feasibility Protocol

The existing audit-session values remain **exploratory**. A final protocol should be agreed before measurement and should report exact software/hardware/thread settings. Proposed practical MSc protocol:

1. **Training:** time each complete tuning-and-refit stage separately from a fresh, documented process; use a fixed seed and fixed search/folds. Run at least five repetitions if practical; report median and interquartile range, candidate count, worker/thread settings, and whether model loading is excluded. If five full searches are impractical, state the reason and use a smaller justified repeat count rather than implying statistical precision.
2. **Inference:** separately time preprocessed `predict_proba` on one row and batches of 16, 64, and the full test size (137), where valid. Include a warm-up (e.g., 20 calls), then enough repeated calls for a stable timing resolution (e.g., 200 single-row calls); report median/IQR and per-row batch time. Keep model loading, feature preparation and prediction as separate measurements, plus an optional end-to-end number.
3. **Explanation generation:** separately time SHAP and LIME explanation generation for one row and a defined batch; state explainer/background setup time separately from per-case explanation time. Fix seeds/settings and report fidelity/validity checks alongside time.
4. **Memory:** measure process-tree RSS at a stated sampling interval from pipeline start through completion, including child workers spawned by `n_jobs`; report peak and sampling method. Also report per-phase peak if practical. Validate the process-tree sampler on macOS and clarify whether memory includes Python, libraries, loaded model, and workers. A post-run snapshot is not peak memory.
5. **Reproducibility:** save raw repetitions or summary inputs, environment, CPU, OS, memory, BLAS/OpenMP settings, batch sizes, and script version in versioned outputs. Never overwrite `results/artifacts/computational_report.json` during this work.

The current 17.02 MB and single-session latencies must remain labelled audit/exploratory values. The proposed protocol is a plan; its timing resolution and full process-tree memory implementation require a brief feasibility test before full measurement.

## K. Decisions Requiring Approval

1. **Prediction time and feature cutoff:** Is the prediction point immediately before loan issuance, and should same-day transactions be excluded by using `transaction_date < loan_date` unless reliable within-day evidence is found?
2. **No-history policy:** If strict cutoff leaves a loan with no prior transactions, should the approved treatment be a missing-history indicator/imputation, a separately reported exclusion sensitivity analysis, or another justified policy? The choice must not be made after comparing test metrics.
3. **Target and horizon:** Does the dissertation retain A/B/C/D mapping as a snapshot status-derived target if no fixed horizon can be substantiated, or should any alternative target be investigated as an explicitly separate estimand? No completed-only target should replace the primary target without approval.
4. **Primary split and tied dates:** Preserve exact current test rows (recommended) while documenting date ties, or approve a tie-aware date cutoff that may alter split membership? Any changed test membership is a methodological change and must not be metric-driven.
5. **Inner CV:** Approve feasible expanding-window/forward-chaining CV inside training as a refinement to the unspecified approved CV procedure? What minimum positive counts/fold feasibility criterion should govern the number of folds?
6. **Model/threshold selection:** Which validation selection criterion is approved? Is a non-0.5 threshold required, and what validation-only criterion should choose it in the absence of institution-specific loss/cost evidence?
7. **Final estimator fit:** Keep final estimators trained on train only after validation selection (recommended for a clean independent role), or approve any train+validation refit and a defensible threshold-transfer procedure?
8. **Explainability scope:** Approve XGBoost as the primary model for SHAP/LIME analysis, the proposed limited dependence features, and three deterministic validation local cases? Should LIME compare only the selected model or all three models?
9. **Stability scope:** Approve refitted time-aware fold models with a common validation reference cohort, with the limitation that validation is also used for model selection? Is similar-case variability required for the final implementation or documented as future work?
10. **Framework contribution wording:** Present the result as (a) a reusable architectural prototype demonstrated on one dataset, with institution-specific adaptation guidance, or (b) a more fully configurable software framework requiring additional implementation? The present evidence supports (a); choice (b) expands scope.
11. **Optional robustness work:** Approve any rolling-origin, completed-contract-only, uncertainty-interval, or split-tie sensitivity analysis individually. Each remains supplemental and separately labelled.

## Recommendation Before Chapter Finalisation

Resolve the prediction-time cutoff and target semantics before finalising Chapter 4: these control whether the empirical task is genuinely pre-issuance default prediction or only prediction of a snapshot status label. Also correct the training/validation procedure and freeze the threshold without test access before presenting corrected test results. Keep the primary test unchanged and describe its three defaults as a severe evidence limitation, not something to repair by resampling.

Missing LIME/dependence analyses, refitted stability, rigorous computational benchmarking, and institution-adaptation documentation should be completed if they are explicit approved dissertation deliverables; otherwise they can be stated transparently as limitations/future work in Chapters 5–6. Lesotho-specific requirements and recommendations must be grounded in literature or actual stakeholder evidence, while performance generalisability, fairness, user comprehension, and credit-loss impact remain untested unless separately evaluated with appropriate evidence.
